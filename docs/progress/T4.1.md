# T4.1 progress — home installers

Status: built and tested (see "Verification"). Read by T4.4 (docs): the commands below are exactly what users run.

## What users run

**macOS** (as yourself, not root; a LaunchAgent in your login session):

```sh
curl -fsSL https://raw.githubusercontent.com/devXpro/gpt-home/main/install/home.sh | bash
```

**Linux / Raspberry Pi** (root; systemd; Raspberry Pi OS 64-bit recommended, 32-bit armv7 works, armv6 boards do not):

```sh
curl -fsSL https://raw.githubusercontent.com/devXpro/gpt-home/main/install/home.sh | sudo bash
```

**Docker (NAS)**, Linux hosts only:

```sh
docker run -d --name gpt-home --restart unless-stopped --network host -v gpt-home:/data ghcr.io/devxpro/gpt-home
docker exec gpt-home homed admin firstrun            # first-run page address and PIN
docker exec -i gpt-home homed relay connect -        # then paste the connect code
```

**Homebrew** (macOS alternative, T4.2): `brew tap devxpro/gpt-home https://github.com/devXpro/gpt-home && brew install
gpt-home && brew services start gpt-home`. Use brew OR home.sh, not both: the hub's in-app self-update replaces the binary
in the Cellar and the next `brew upgrade` puts the brew version back.

Options go after `bash -s --`, for example `... | sudo bash -s -- --version v0.1.0`:

| Flag | Meaning |
|---|---|
| `--version vX.Y.Z` | that release (default: the latest, found through the `/releases/latest` redirect, no API rate limit) |
| `--prefix DIR` | macOS: binary at `DIR/bin/homed` (default `~/Library/Application Support/gpt-home`). Linux: command `DIR/bin/homed`, program `DIR/lib/gpt-home/homed` (default `/usr/local`) |
| `--no-start` | install the files only, never touch launchd or systemd (also for uninstall) |
| `--dry-run` | print release, archive, URL, sha256 and target; download only `checksums.txt`; change nothing |
| `--uninstall` | stop and remove the service, the program and the command; keeps the data (and, on Linux, the user) |
| `--purge` | with `--uninstall`: also delete the data and, on Linux, the user `gpt-home` (asks first) |
| `--yes` | no questions (uninstall and purge ask otherwise; install never asks) |
| tests only | `--release-base URL`, `--allow-http`, `--os`, `--arch`, `--label` |

Re-running the installer is the update: the data stays, the service restarts only when the binary, the unit or the plist
changed (otherwise "Already installed and running; nothing to restart.").

## What it does

Release assets (T4.2, final): `homed_<version>_<os>_<arch>.tar.gz` (version without `v`; os darwin|linux; arch amd64,
arm64, armv7; `homed`, LICENSE, README.md at the top level) and `checksums.txt`. The script reads checksums.txt first
and picks the archive that is listed there (armv7, then armv6, then arm, the same order as `internal/install`), checks
the sha256, refuses archive entries that are absolute or contain `..`, accepts a wrapped archive too, and runs
`homed version` from the staging dir before it installs anything. Only https (also across redirects) unless
`--allow-http`. The unit, the plist and the CLI wrapper are templates in `install/`; they come from the checkout the
script lives in, or (curl | bash) from `raw.githubusercontent.com/devXpro/gpt-home/<release tag>/install/...`
(`GPT_HOME_REF` overrides the tag).

### macOS

- `~/Library/Application Support/gpt-home/bin/homed` (0755; the previous binary stays as `homed.prev`), the data dir
  `~/Library/Application Support/gpt-home` (0700), logs `~/Library/Logs/gpt-home/homed.log`.
- LaunchAgent `~/Library/LaunchAgents/com.github.devxpro.gpt-home.homed.plist` from
  `install/launchd/com.github.devxpro.gpt-home.homed.plist`: `RunAtLoad`, `KeepAlive`, `ThrottleInterval 10`, and
  `HOMED_DATA_DIR` set explicitly (launchd runs the agent with the real HOME, so the default would be the same dir).
  `launchctl bootstrap gui/<uid>`, `kickstart -k` on an update, `bootout` + `bootstrap` when the plist changed.
- After a first install the script waits for homed's socket and prints `homed admin firstrun` (the first-run page
  address and the PIN); then the one-time Local Network prompt (click Allow; if missed: System Settings > Privacy &
  Security > Local Network, then `launchctl kickstart -k gui/$(id -u)/com.github.devxpro.gpt-home.homed`), the next
  steps with full paths (homed is not on PATH): `'<bin>' relay connect -` (code via stdin), `'<bin>' admin setup-link`,
  `'<bin>' admin firstrun`, the Homebrew alternative and the self-update warning.
- Refuses to run as root.

### Linux / Raspberry Pi

- System user `gpt-home` (`useradd --system`, nologin shell, home `/var/lib/gpt-home`), data dir `/var/lib/gpt-home`
  (0700, `HOMED_DATA_DIR`).
- Program `/usr/local/lib/gpt-home/homed` (0755, **owned by gpt-home**, `homed.prev` kept) and the command
  `/usr/local/bin/homed`, a small root-owned shell wrapper (`install/systemd/homed.wrapper`).
  Why: the hub's self-update (admin > Settings > Updates) swaps its own binary and exits 75, so the service user must be
  able to write the binary's directory; and the CLI must run as that user on that data dir (its socket is 0600 and
  checks the peer uid). The wrapper makes `homed relay connect -` work from any sudo account (it runs
  `sudo -u gpt-home env HOMED_DATA_DIR=/var/lib/gpt-home <program> ...`, or `runuser` as root); `sudo -u gpt-home homed ...`
  works too. It never runs the program as root; `homed version`/`--help` run directly for everyone. A pre-existing
  `/usr/local/bin/homed` that is not ours makes the installer stop.
- Unit `/etc/systemd/system/gpt-home.service` from `install/systemd/gpt-home.service`: `User=gpt-home`,
  `Restart=always` (exit 75 after a hub update restarts it), `Environment=HOMED_DATA_DIR=/var/lib/gpt-home`, hardening
  (NoNewPrivileges, empty capability set, ProtectSystem=strict with ReadWritePaths for the data and program dirs,
  ProtectHome, PrivateTmp, PrivateDevices, kernel/cgroup/clock/hostname protections, RestrictSUIDSGID, RestrictNamespaces,
  RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6 AF_NETLINK, UMask 0077). No PrivateNetwork and no IPAddressDeny: SSDP
  multicast, UDP broadcast (Wake-on-LAN) and the ARP table keep working (tested).
  `systemctl enable` + `restart`, waits for `active`, checks again after 2 s.
- After a first install it prints the first-run page address and PIN (through the wrapper, `homed admin firstrun`) and
  the next steps: `homed relay connect -`; `homed admin setup-link` (works from any browser) or `homed admin firstrun`
  (LAN page on port 8090; once the relay is connected the page listens on the loopback only); status
  `systemctl status gpt-home`, logs `journalctl -u gpt-home -f`.
- Needs root, `curl tar install useradd getent awk find cmp`, and a running systemd (or `--no-start`).
- 32-bit userland on a 64-bit kernel (`uname -m` says aarch64, `getconf LONG_BIT` says 32) gets the armv7 build.

### Docker

`Dockerfile` (repo root) is the **release** image GoReleaser builds (`dockers_v2`): single stage, `COPY $TARGETPLATFORM/homed`,
Alpine 3.22 + ca-certificates + tzdata + tini, user uid 10001, `HOMED_DATA_DIR=/data` (volume, 0700), root-owned
read-only binary (so the admin's self-update says "not writable"; update by pulling a new image), `HEALTHCHECK` on
`127.0.0.1:8080/healthz`, `ENTRYPOINT tini -- homed`, `CMD run`. `Dockerfile.dev` builds from the sources (SPA with
Node 22, Go `golang:1.26.11-alpine` = the go.mod toolchain, ldflags `VERSION`/`COMMIT`): `docker build -f Dockerfile.dev -t gpt-home:dev .`.
`.dockerignore` serves that build only.

`--network host` is required: discovery is SSDP multicast and wake is a UDP broadcast, neither passes the NAT of the
default bridge network. Docker Desktop on macOS runs containers in a Linux VM, so "host" is the VM, not the Mac's LAN:
use the brew formula or home.sh on a Mac. For a bind mount: `chown 10001:10001 DIR`.

## Tests (`install/test/`)

```sh
install/test/run.sh            # lint + mac + linux (all)
install/test/run.sh lint       # shellcheck of home.sh, the wrapper and the tests
install/test/run.sh mac        # macOS, temp HOME
install/test/run.sh linux      # Docker: Debian containers gpthome-t41-*
PLATFORMS="linux/amd64" SYSTEMD_PLATFORMS="" KEEP_IMAGES=1 install/test/run.sh linux
```

- `fakerelease.py` (stdlib only, run from a venv the script makes in a temp dir): a fake GitHub release server with the
  real shapes (`/latest` redirect, `/download/<tag>/...`, `/raw/<ref>/install/...`) and releases v0.0.1 (flat),
  v0.0.2, v0.0.3 (wrapped archives), v0.0.4 (checksum mismatch), v0.0.5 (archive with a `../evil` entry), v0.0.6 (linux
  arm64 only). The "homed" in the archives is a shell script (`version`, `run`, `admin firstrun`, `env`).
- mac: part 1 with `--no-start` in a temp HOME and a `launchctl` shim that fails the test on any call: files, modes,
  `plutil -lint`, every plist key, re-run no-op, update, `.prev`, refusals, wrapped archive, `--prefix` with a space,
  uninstall keeps data, `--purge`; the real LaunchAgent's checksum and pid are compared before and after. Part 2 starts
  the fake homed under real launchd with the TEST label `com.github.devxpro.gpt-home.homed.t41` in a temp HOME (never the real
  label): first-run output, re-run no-op, update restart, exit 75 restart, uninstall.
- linux: `Dockerfile.linux` (Debian bookworm; target `base` = curl + sudo, target `systemd` adds systemd + socat) on every platform in `PLATFORMS`
  (default native + amd64 through Rosetta; arm/v7 is opt-in, its image takes 30+ minutes under qemu): `--no-start` flows (user, modes, owners, unit content,
  `systemd-analyze verify`, the wrapper as root / as gpt-home / as an unprivileged user with and without sudo rights,
  idempotent re-run, update, refusals, foreign file at the command path, curl | bash with templates from the raw URL,
  `--prefix` with a space, uninstall, purge, not-root refusal) and, on `SYSTEMD_PLATFORMS`, the same container booted
  with systemd as PID 1: real start, process owner, loaded hardening, UDP broadcast and multicast join from inside the
  sandbox, restart after exit 75, no-op re-run keeps the PID, update, uninstall.
